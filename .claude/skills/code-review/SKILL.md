# code-review — Pn 룰 기반 코드리뷰

이 프로젝트에서 요구사항 구현이 끝날 때마다 실행하는 코드리뷰. **서브에이전트로 실행**하며, 리뷰어는 구현자와 독립된 시각으로 평가한다.

## 사전 준비 (리뷰 전 필수)

1. 프로젝트 루트 `CLAUDE.md`를 읽고 모든 규약(계층/인터페이스/DTO/테스트/설정/DDL)을 숙지한다.
2. tech-spec/요구사항 문서를 읽는다: **`.claude/tech-spec/` 폴더의 해당 기능 md**가 1순위, 없으면 리뷰 요청 시 전달받은 요구사항 텍스트.
3. 리뷰 대상 파일 목록을 파악한다: git 저장소면 `git diff`/`git status` 기준, 아니면 리뷰 요청에 명시된 이번 작업의 변경/추가 파일.

## 중점 점검 항목 (7가지)

1. **컨벤션 위반**: CLAUDE.md 규약 위반 여부. 계층 규약(참조 방향, DTO 공유 금지, Command/도메인 반환), 인터페이스 규약(nested 구현체), DTO 규약(@Schema name/description/nullable), 테스트 규약(service 중심, JUnit 포맷, kotest/mockk), 설정/DDL 규약.
2. **유사 코드/변수명 중복 정의**: 기존 코드에 이미 있는 것과 비슷한 함수·클래스·컴포넌트·변수명을 새로 만들지 않았는지. Grep으로 유사한 이름(동의어 포함: get/find/fetch, create/add/register 등)을 검색해 확인한다. 기존 것을 재사용하거나 확장해야 할 자리에 신규 정의가 있으면 지적.
3. **하위호환성 / breaking change**: 기존 API 경로·HTTP 메서드·요청/응답 필드(이름·타입·nullable) 변경, 삭제, 의미 변경. 설정 키 변경, DB 스키마 파괴적 변경(컬럼 삭제/타입 변경), 공개 인터페이스 시그니처 변경. 신규 추가는 OK, 기존 계약 변경은 지적.
4. **tech-spec 불일치**: 요구사항 문서와 구현이 다른 부분. 빠진 요구사항, 스펙에 없는 임의 추가 기능, 스펙과 다른 동작(엣지 케이스 처리 포함).
5. **구조적 결함**: 동시성 문제(공유 가변 상태, non-atomic 연산), 에러 처리 누락, 트랜잭션 경계 오류, 계층 침범, 테스트 불가능한 구조, 명백한 성능 문제(N+1 등).
6. **기존 구현 소실(회귀) — 특히 조심**: 새로운 명령/요구사항을 반영하면서 **이전에 구현된 내용이 뭉개져 사라지지 않았는지** 반드시 확인한다. 파일 전체 재작성(Write)이 있었던 파일은 특히 의심. 점검 방법:
   - git 저장소면 `git diff`에서 **삭제된 라인**을 훑어 의도된 삭제인지 확인.
   - tech-spec의 요구사항 목록·이전 리뷰에서 "반영됨"으로 확인된 항목들이 현재 코드에 여전히 존재하는지 대조.
   - 컨트롤러 엔드포인트 수, 서비스 메서드, 테스트 케이스 수가 직전 대비 줄었다면 사유를 확인.
   - **의도 불명의 기능 소실은 무조건 P1**이다.
7. **SOLID 원칙 — 확장 가능하고 유연한 구조인지**:
   - SRP: 한 클래스/메서드가 여러 책임을 지고 있지 않은지 (단, 프로젝트 규약상 과도한 분해도 지양 — 응집 우선).
   - OCP: 서브 구현체가 여러 개 나올 수 있는 지점이 if/when 타입 분기로 처리되어 있으면 지적 — 전략 패턴(인터페이스 + `List<Strategy>` 주입)으로 유도.
   - LSP/ISP: 구현체가 인터페이스 계약(KDoc의 비즈니스 규약 포함)을 어기거나, 인터페이스가 비대해 일부 구현체가 빈 구현을 갖는지.
   - DIP: 구체 클래스 직접 의존(구현체 주입, `*JpaRepository` 직접 사용 등)이 없는지.

## Pn 룰 (평가 등급)

모든 지적사항에 반드시 Pn 등급을 붙인다:

| 등급 | 의미 | 기준 |
|---|---|---|
| **P1** | 반드시 수정 (머지 블로커) | 규약 위반, breaking change, spec 불일치, 버그/심각한 구조 결함 |
| **P2** | 적극 반영 권장 | 잠재 버그 소지, 중복 정의, 하위호환 리스크 |
| **P3** | 가능하면 반영 | 구조 개선, 가독성 |
| **P4** | 사소한 제안 (nit) | 네이밍, 스타일 (ktlint가 못 잡는 것) |
| **P5** | 질문/의견 | 의도 확인, 대안 제시 |

## 출력 형식

```
## 코드리뷰 결과

**P1: N건 / P2: N건 / P3: N건 / P4: N건 / P5: N건**

### P1
- [P1] `파일:라인` — 지적 내용. 근거(어느 규약/스펙 조항). 수정 제안.
### P2
...

### DECISION NEEDED (있는 경우만)
- 사용자 의사결정이 필요한 항목 (예: 스펙이 모호함, 의도적 breaking change 여부 확인 필요)
```

- 지적할 게 없으면 "P1: 0건 — 통과" 를 명시한다.
- **사용자 판단이 필요한 사항은 P1로 올리지 말고 DECISION NEEDED로 분리**한다.

## 반복 규칙 (오케스트레이터가 수행)

1. 구현 완료 → 이 스킬을 서브에이전트로 실행.
2. P1이 있으면 수정 후 재리뷰. **P1이 0건이 될 때까지 반복**.
3. DECISION NEEDED가 나오면 **루프를 멈추고 사용자에게 물어본다**.
4. P1 = 0 이 되면 `./gradlew ktlintFormat ktlintCheck test koverVerify` 실행 후 결과를 보고한다.
